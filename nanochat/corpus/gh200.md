# Corpus: actions before and after the GH200

The corpus pipeline splits at the tokenizer (`normalization_doc.md` §10). Everything through curation is text and
runs on the GB10; the curated shards go to the private Hub dataset `iaroy/nanochat-data` (`config.DATASET`). The
tokenizer ablation and decision, compile, pack and training run on the GH200 from a pull of that dataset.

Every command runs in the `nanochat` image (`docker build -f docker/Dockerfile -t nanochat .`) from the repository's
root, through `runs/container.sh` on the GH200 (`runs/setup.sh` prepares a fresh host and pulls the dataset) or, on
the GB10:

```
docker run --rm --user $(id -u):$(id -g) -e HOME=/tmp -e PYTHONPATH=/workspace/nanochat -w /workspace/nanochat \
  -v $PWD:/workspace/nanochat nanochat python -m nanochat.corpus.<step> ...
```

Steps that read the Hub add `-e HF_HOME=/tmp/hf -e HF_HUB_DISABLE_XET=1 -e HF_TOKEN=$(hf auth token | tail -1)`.

## Before the GH200 (GB10)

1. **Prepare**: `python -m nanochat.corpus.prepare` fetches and standardizes every source (`normalization_doc.md` §1);
   fetched files are kept, so a rerun downloads only Hub files it does not hold. A source read in part fetches its
   extent (`prepare.extent`).
2. **Curate**: `python -m nanochat.corpus.curate`: the Python 3 check with repair, exact deduplication, the split, the
   curated shards (`CORPUS/curated/<source>/<split>/<k>.parquet`; `normalization_doc.md` §4, whose invariants are
   checked on every row before publication).
3. **Publish**: `python -m nanochat.corpus.publish push` writes the card, replaces the dataset's tree
   (`<source>/<split>/<k>.parquet` beside `README.md`) and squashes its history into one commit. The card turns the
   Hub's viewer off, so no converted copy of the shards is kept. The dataset is constant from here.

## On the GH200

1. **Code, image and pull**: check out master; `HF_TOKEN=<read token> runs/setup.sh` builds the image, creates
   `artifacts/` and runs `python -m nanochat.corpus.publish pull` (the shards into `CORPUS/curated`).
2. **Tokenizer ablation, intrinsic part and data** (`ablations/tokenizer.md`): `python -m ablations.tokenizer
   vocabularies`, `intrinsic`, `data`. An arm's extent margin (`results/tokenizer-intrinsic.json`) below 1 means a
   group read in part is too small for it: raise `mixture.SPREAD`, then on the GB10 prepare, curate and publish again.
3. **Tokenizer decision**: `python -m nanochat.run experiment=tokenizer` (8 d16 runs in `artifacts/runs/<key>/`, then
   `results/tokenizer.json` `"analysis"` `"decision"`). Needs the user's approval.
4. **Adopt the tokenizer**: `python -m ablations.tokenizer adopt` writes the decided vocabulary to `CORPUS/tokenizer`;
   every later step reads it.
5. **Compile**: `python -m nanochat.corpus.compile`; it ends with the 32K stage's repository partitions
   (`compile.compile_stage`).
6. **Pack**: `python -m nanochat.corpus.pack`; it packs each stage's rows and stops naming any source that holds fewer
   rows than its draw (`pack.fit`).
7. **Smoke**: the first micro-batches of both stages (`loader.PretrainingBatches` at the stages' weights), decoded;
   each step's group composition and FIM share.
8. **Train**: `python -m nanochat.run experiment=base` (records in `results/base.jsonl` and `base-curves.jsonl`).
   Needs the user's approval.
