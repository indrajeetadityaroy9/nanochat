# Corpus: actions before and after the GH200

The corpus pipeline splits at the tokenizer (`normalization_doc.md` §10). Everything through curation is text and
runs on the GB10; the curated shards go to the private Hub dataset `iaroy/nanochat-data` (`config.DATASET`). The
tokenizer ablation and decision, compile, pack and training run on the GH200 from a pull of that dataset. Packing and
FIM cannot run before: packing places pieces in rows of `seq_len` tokens and cuts them at token offsets
(`nanochat/data/crate/src/pack.rs`), FIM encodes prefix, suffix and middle separately around sentinel ids, and the 32K
stage's partitions are counted in tokens (`compile.stage_parts`).

Every command runs in the `nanochat` image (`docker build -f docker/Dockerfile -t nanochat .`) from the repository's
root:

```
docker run --rm --user $(id -u):$(id -g) -e HOME=/tmp -e PYTHONPATH=/workspace/nanochat -w /workspace/nanochat \
  -v $PWD:/workspace/nanochat nanochat python -m nanochat.corpus.<step> ...
```

Steps that read the Hub add `-e HF_HOME=/tmp/hf -e HF_HUB_DISABLE_XET=1 -e HF_TOKEN=$(hf auth token | tail -1)`.

## Before the GH200 (GB10)

1. **Prepare every read source** (`mixture.READ`): `python -m nanochat.corpus.prepare <source> ...`. A source is
   prepared once (its standardized directory must not exist); raw files already present are not downloaded again, so a
   rerun after deleting `CORPUS/standardized/<source>` only re-standardizes. Each source's revision, files and rows go
   to `CORPUS/manifest.json`.
   - Sources read in part fetch their extent (`prepare.extent`, `normalization_doc.md` §1).
   - Stack-v3-L2's 75 raw files were written from production's whole Hub files
     (`nanochat-runs/data/raw/ultradata_stack_v3_l2_*`), each sha256-identical to the Hub's LFS object at the revision
     prepare reads (`62077439`), as `prepare.fetch` writes them.
   - Stack-Edu's text comes from Software Heritage's bucket (measured: 1,968 blobs a second per process); it runs in
     its own container, beside the Hub downloads.
2. **Curate**: `python -m nanochat.corpus.curate`. The Python 3 check with repair, exact deduplication over every read
   source, the split, the curated shards (`CORPUS/curated/<source>/<split>/<k>.parquet`).
3. **Verify the curated shards** before they leave the machine (done on every row, `normalization_doc.md` §4):
   - every text non-empty, without CR or a leading U+FEFF; a document's `id` its sha1; no two rows with one text
     across every source and split;
   - every Python file (a repository's, a synthetic one, a function) parsing (a sample per shard);
   - one schema per source; no repository and no Codeforces problem in both splits;
   - each source's curated rows equal to its input rows less its duplicates (curate prints both).
4. **Publish**: `python -m nanochat.corpus.publish push`. It writes the code's commit and each split's shards, rows
   and text bytes into the manifest, writes the card, replaces the dataset's tree (`curated/**`, `manifest.json`,
   `README.md`) and squashes its history into one commit, whose sha it prints: published as
   `ff038dcd95a40833797e3ea4fbc1a02422bb3f62` (manifest code `52c28f7`). The card turns the Hub's viewer off, so no
   converted copy of the shards is kept. The dataset's previous contents (production's curated and compiled data) were
   deleted beforehand; production's `config.DATASET_REVISION` (`7a210ed3`) no longer exists on the Hub, and
   production's data remains only in `nanochat-runs/data` on the GB10.

## On the GH200

1. **Code and image**: check out the commit in the dataset's `manifest.json` (`"code"`), build the image.
2. **Pull**: `python -m nanochat.corpus.publish pull --revision ff038dcd95a40833797e3ea4fbc1a02422bb3f62` (a token with
   access to the private dataset).
   `CORPUS/curated` and `CORPUS/manifest.json` are then as the GB10 left them: each split's shards and rows equal
   `manifest.json`'s `curated` entry (Parquet footers).
3. **Tokenizer ablation and decision.** `ablations/tokenizer.py` reads `nanochat/data`'s compiled corpus and
   production's equal-bytes sample; port it to the corpus first: its sample from `corpus/tokenizer.sample`, its document
   sets from the curated shards, its compile and pack from `corpus/compile` and `corpus/pack`. Its decision sets the
   corpus tokenizer's pattern and score (`corpus/tokenizer.py` trains production's `SPLIT_PATTERN` and SA-BPE).
4. **Train the tokenizer**: `python -m nanochat.corpus.tokenizer`. It reports each source's bytes per token against
   production's and, for each group read in part, its train tokens over its draw. Below 1, the group's extent is too
   small: raise `mixture.SPREAD`, then on the GB10 delete the group's `CORPUS/standardized/<source>` directories,
   prepare them again (only the new Hub files download), curate and publish again.
5. **Compile**: `python -m nanochat.corpus.compile`; it ends with the 32K stage's partitions and their tokens.
6. **Pack**: `python -m nanochat.corpus.pack`; it writes `CORPUS/packed.json` (each stage's rows and weights) and
   stops naming any source that holds fewer rows than its draw.
7. **Smoke**: the first micro-batches of both stages (`loader.PretrainingBatches` over `packed.json`'s weights),
   decoded; each step's group composition and FIM share.
8. **Cutover** (`normalization_doc.md` §10): point `config`, `train/stages`, `train/loop`, `eval/bpb`,
   `eval/code_eval`, `eval/suite`, `inference/decoder`, `inference/syntax_constraint`, `ops/cross_entropy` and
   `scripts/production` at `nanochat.corpus`; move `nanochat/data/crate` to `nanochat/corpus/crate`; delete
   `nanochat/data`; remove go-enry from `docker/Dockerfile`.
9. **Train.**
