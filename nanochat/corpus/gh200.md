# Corpus: actions before and after the GH200

The corpus pipeline splits at the tokenizer (`normalization_doc.md` §10). Everything through curation is text and
runs on the GB10; the curated shards go to the private Hub dataset `iaroy/nanochat-data` (`config.DATASET`). The
tokenizer ablation and decision, compile, pack and training run on the GH200 from a pull of that dataset. Packing and
FIM cannot run before: packing places pieces in rows of `seq_len` tokens and cuts them at token offsets
(`nanochat/data/crate/src/pack.rs`), FIM encodes prefix, suffix and middle separately around sentinel ids, and the 32K
stage's partitions are counted in tokens (`compile.stage_parts`).

Every command runs in the `nanochat` image (`docker build -f docker/Dockerfile -t nanochat .`) from the repository's
root:

```
docker run --rm --user $(id -u):$(id -g) -e HOME=/tmp -e PYTHONPATH=/workspace/nanochat -w /workspace/nanochat \
  -v $PWD:/workspace/nanochat nanochat python -m nanochat.corpus.<step> ...
```

Steps that read the Hub add `-e HF_HOME=/tmp/hf -e HF_HUB_DISABLE_XET=1 -e HF_TOKEN=$(hf auth token | tail -1)`.

## Before the GH200 (GB10)

1. **Prepare**: `python -m nanochat.corpus.prepare`. It prepares every source whose manifest entry differs from its
   extent (a new source, or one whose mixture share changed); fetched files are kept, so only new Hub files download.
   Each source's files and rows go to `CORPUS/manifest.json`.
   - Sources read in part fetch their extent (`prepare.extent`, `normalization_doc.md` §1).
   - Stack-v3-L2's 75 raw files were written from production's whole Hub files
     (`nanochat-runs/data/raw/ultradata_stack_v3_l2_*`), each sha256-identical to the Hub's LFS object, as
     `prepare.fetch` writes them.
   - Stack-Edu's text comes from Software Heritage's bucket (measured: 1,968 blobs a second per process).
2. **Curate**: `python -m nanochat.corpus.curate`. The Python 3 check with repair, exact deduplication over every read
   source, the split, the curated shards (`CORPUS/curated/<source>/<split>/<k>.parquet`).
3. **Verify the curated shards** before they leave the machine (done on every row, `normalization_doc.md` §4):
   - every text non-empty, without CR or a leading U+FEFF; a document's `id` its sha1; no two rows with one text
     across every source and split;
   - every Python file (a repository's, a synthetic one, a function) parsing (a sample per shard);
   - one schema per source; no repository and no Codeforces problem in both splits;
   - each source's curated rows equal to its input rows less its duplicates (curate prints both).
4. **Publish**: `python -m nanochat.corpus.publish push`. It writes the code's commit and each split's shards, rows
   and text bytes into the manifest, writes the card, replaces the dataset's tree (`CORPUS/curated`'s tree at the
   root, `<source>/<split>/<k>.parquet`, beside `manifest.json` and `README.md`) and squashes its history into one
   commit. The card turns the Hub's viewer off, so no converted copy of the shards is kept. The dataset is constant from
   here; production's earlier contents are gone from the Hub and remain only in `nanochat-runs/data` on the GB10.

## On the GH200

1. **Code and image**: check out master and build the image. The manifest's `"code"` names the commit that published
   the shards; the corpus code after it reproduces the same curated rows and downstream outputs (verified old against
   new on a sandbox of every source).
2. **Pull**: `python -m nanochat.corpus.publish pull` (a token with access to the private dataset): the shards into
   `CORPUS/curated`, the manifest into `CORPUS`, as the GB10 left them; each split's shards and rows equal
   `manifest.json`'s `curated` entry (Parquet footers), and its `bytes` are the `content` column's uncompressed size,
   each value's 4-byte length prefix included (the publishing commit's count; `sources.text_bytes` plus 4 per row).
3. **Tokenizer ablation, intrinsic part** (`ablations/tokenizer.py`): `python -m ablations.tokenizer vocabularies`
   trains its four arms at once on the corpus tokenizer's sample into `CORPUS/tokenizer-ablation/<arm>` (the
   vocabulary and its merges) and writes `results/tokenizer-vocabularies.json` (the sample's composition, each arm's
   training time); `python -m ablations.tokenizer data` compiles every arm's val splits into
   `CORPUS/tokenizer-ablation/compiled` and writes their intrinsic record, `results/tokenizer-data.json` (compression,
   vocabulary, coverage, depth invariance, train/encode fidelity, TokEval's metrics, overlap between arms).
4. **Cutover** (`normalization_doc.md` §10): point `config`, `train/stages`, `train/loop`, `eval/bpb`,
   `eval/code_eval`, `eval/suite`, `inference/decoder`, `inference/syntax_constraint`, `ops/cross_entropy`,
   `ablations/harness`, `ablations/lr` and `scripts/production` at `nanochat.corpus`; give the ablation's runs their
   document set and every arm's packs (`compile` and `pack` take the arm's tokenizer); move `nanochat/data/crate` to
   `nanochat/corpus/crate`; delete `nanochat/data`; remove go-enry from `docker/Dockerfile`.
5. **Tokenizer decision**: `python -m ablations.tokenizer runs` (8 d16 runs, then `results/tokenizer.json`
   `"decision"`); the decision sets `corpus/tokenizer.py` `PATTERN` and `SCORE`.
6. **Train the tokenizer**: `python -m nanochat.corpus.tokenizer`. It reports each source's bytes per token against
   production's and, for each group read in part, its train tokens over its draw (with production's pattern and score,
   1.096, 1.071 and 1.169: `normalization_doc.md` §9). Below 1, the group's extent is too small: raise
   `mixture.SPREAD`, then on the GB10 run prepare (it prepares again exactly the sources whose extent grew; only the
   new Hub files download), curate and publish again.
7. **Compile**: `python -m nanochat.corpus.compile`; it ends with the 32K stage's partitions and their tokens.
8. **Pack**: `python -m nanochat.corpus.pack`; it writes `CORPUS/packed.json` (each stage's rows and weights) and
   stops naming any source that holds fewer rows than its draw.
9. **Smoke**: the first micro-batches of both stages (`loader.PretrainingBatches` over `packed.json`'s weights),
   decoded; each step's group composition and FIM share.
10. **Train.**
